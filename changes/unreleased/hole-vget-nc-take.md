### Security

- **A `vec_get` payload that cannot be copied is no longer taken out of its Vec where it would leave a value that is none.** A payload whose type has no copy and whose all-zero bytes are no value of it (a struct holding a trait object, a closure or a library handle), handed from its `??` arm to a callee that keeps it (`?? ( vec_get [Pet] vs 0 ) { T p → { ( vec_push [Pet] ws p ) } … }`), was taken out of its slot: the Vec kept zero bytes there, and a later method call through that element called a null vtable (SEGV). Such a store is now judged at module end, on the callee's final summary, as a store of what a call lends, and refused where the callee keeps or releases the value (the message names `vec_remove` / `vec_pop`). A callee that only reads it compiles as before, and a type whose all-zero value is one is taken out as before. New tests `diag_nc_vec_get_payload_stored_from_its_arm`, `diag_nc_vec_get_payload_stored_by_a_forwarder`, `nc_vec_get_payload_read_in_its_arm`; hole probe `vec_get_noncopyable_payload_stored_leaves_a_null_slot`.
  - **Migration:** a program refused now crashed before when it read the element again. Take the element out of the Vec (`?? ( vec_remove [Pet] vs 0 ) { T p → … }`, `vec_pop`) and store that. No in-repo program changes.
