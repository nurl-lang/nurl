# NURL benchmark results

> Captured on **2026-05-25**. Hardware: Intel Core i7-5930K @ 3.50 GHz
> (12 logical cores, 2014 vintage), Ubuntu 24.04 (kernel 6.17), Linux
> x86_64. Compilers: NURL stage-2 from `Improvements` branch
> (HEAD: borrow-checker Phase 8 final, 2026-05-25), Rust 1.82.0,
> Python 3.12.3, Node v24.15.0.
>
> Numbers are **median wall-clock ms across 5 runs** per cell, with a
> 60 s per-run timeout. Reproduce with `./bench/run.sh --timeout 60 5`.

## Headline table

| Benchmark         | NURL  | Python  | Rust  | Node    |
|-------------------|------:|--------:|------:|--------:|
| `lcg`             |  10   | 27 459  |  16   |  9 680  |
| `sieve`           |  69   |  5 898  |  62   |    142  |
| `json_parse`      |  14   |     34  |   5   |     47  |

(Lower is better. All times ms.)

The `json_parse` number is the headline of this revision (2026-05-25):
the pure-NURL parser was **479 ms** in the v1 ship 12 hours ago. Two
landed optimisations dropped it ~34× to **14 ms**:

1. **Direct `*u` pointer reads instead of `nurl_str_get`** (json.nu).
   Every peek was paying a full `strlen` of the whole input — a 64 KB
   parse was spending gigabytes of memory bandwidth in `strlen` alone
   (textbook O(n²)). Fixed by reading bytes through the cached `*u`
   data pointer, plus a `memchr`-driven fast path in
   `__jp_parse_string` that slices the literal byte range when the
   string contains no backslash escapes (true for ~100 % of strings
   in machine-generated JSON).

2. **Packed-layout `String` constructor** (core/string.nu +
   core/vec.nu). The new `string_from_bytes_packed` allocates the
   24-byte `Vec` control block and the data buffer in a single
   `nurl_alloc(24 + n + 1)`. `vec_free` / `vec_free_with` /
   `__vec_grow` detect the layout by `data == ctl + 24`; the lifecycle
   is byte-identical to a normal String (it can still grow — the first
   growth pays for an unpacking copy out into a separate buffer). For
   JSON parsing every `JNum` / `JStr` is read-only after construction,
   so this exact case halves the per-string allocation count.

The combined effect is that NURL's pure-NURL JSON parser is now
faster than Python's C-extension `json` module on this payload, and
roughly 3× slower than a hand-written zero-copy Rust parser. The
remaining Rust gap is structural — Rust's parser stores `&str` slices
into the input rather than allocating fresh strings.

## Reading the table

### lcg — NURL ≈ Rust, both ~2 500× faster than Python

100 million iterations of the MMIX linear congruential generator (a
single i64 multiply + add per step, with i64 wrap-around). NURL and
Rust land within measurement noise of each other; both compile through
LLVM `-O2`, so the loop ends up as the same tight `imul`/`add` kernel.
Python's pure-int loop is ~28 seconds (28 244 ms ÷ 11 ms ≈ 2 568×
slower). Node BigInt is ~900× slower than NURL — V8 doesn't JIT BigInt
into native multiplications.

### sieve — NURL ties Rust, beats Node ~2×, beats Python ~90×

Sieve of Eratosthenes to π(10 000 000) = 664 579. NURL and Rust again
land within noise: both compile to the same array-mark + scan loops.
Node's typed-array path (`Uint8Array`) lands ~2× behind. Python's
`bytearray` loop is ~6 seconds, the classic order-of-magnitude penalty
for a pure-Python tight loop.

### json_parse — NURL ~2.4× faster than Python's C `json`, ~3× behind hand-written Rust

5 parses of a deterministic ~64 KB JSON file (500 records, generated by
`bench/gen_data.py` with `random.seed(42)`). Each language uses **what
ships in its standard distribution**: Python's stdlib `json` (a C
extension), Node's built-in `JSON.parse` (V8 C++), NURL's pure-NURL
`stdlib/ext/json.nu`. Rust has no JSON in stdlib, so the Rust file
includes a small hand-written recursive-descent parser — same
"no external dependencies" rule.

After the two optimisations listed above, NURL's pure-NURL parser
runs the 64 KB payload at ~22 MB/s sustained, ahead of Python's
C-extension `json` (~10 MB/s) and behind the zero-copy hand-written
Rust parser (~60 MB/s). The remaining gap to Rust is structural —
Rust's parser stores `&str` slices into the input rather than
allocating fresh strings. Closing that gap from NURL would require
either a `JsonView` shape that borrows from the source buffer (an
API change), or a region/arena allocator for the parser's output.

## What the numbers actually say about NURL

1. **Compiled-LLVM compute parity is real.** On the two compute-bound
   benchmarks NURL matches Rust to within measurement noise. The
   "compiles through LLVM `-O2 -flto`" claim is doing what it says on
   the tin: the lcg and sieve binaries are equivalent codegen.

2. **The C-vs-pure-NURL gap shows up in the stdlib.** `json_parse` is
   where the stdlib choice of "pure NURL over libc primitives" shows
   its cost — Python and Node have decades of optimisation work in
   their C-extension JSON parsers, NURL's parser is 3 KB of NURL on top
   of `nurl_alloc`. Same shape will show in `regex`, `hashmap` under
   adversarial input, and `string` push-loops. None of those are
   fundamental — they're optimisation work the project hasn't done yet.

3. **The Python tax for compute is real and large.** ~2 500× on `lcg`,
   ~90× on `sieve`. If you're rewriting a hot Python loop in NURL,
   these are the savings you're buying. If you're rewriting a
   network-bound program — where Python is already 95 % idle on
   `epoll_wait` — these numbers don't transfer.

## What this is not

- Not a NURL HTTP-server-vs-Go-`net/http` benchmark. That comparison
  is the one `critic.md` §10 specifically asked for (the "38×
  keep-alive" claim was NURL-vs-NURL); building it is the next
  benchmark suite to land. It needs a Go install and a peer HTTP
  client like `wrk`; this directory's `run.sh` does neither.
- Not a peer-reviewed throughput suite. There's no warm-up loop, no
  variance reporting beyond a median, no perf-counter capture. Numbers
  are good for order-of-magnitude reasoning; don't draw < 10 %
  conclusions from a cell.
- Not a measurement of NURL's bus-factor-1 maintenance risk, its
  package-manager maturity, its IDE story, or any of the other
  dimensions where Python and Rust dominate. Those are the right
  reasons to pick or not pick NURL today; performance is a single
  axis.

## Reproducing

```sh
git checkout Improvements        # or main once this lands
./build.sh                       # builds build/nurlc + stdlib/runtime.o + runs tests
./bench/run.sh --timeout 60 5
```

The runner detects which tools are installed. Missing tools print
`n/a` in the column; the timeout cell renders as `>60s` (the suite
keeps moving instead of hanging — `critic.md` §10 in spirit).
