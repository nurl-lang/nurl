# Tokeniser-aware token efficiency

> Generated by `bench/token_efficiency.py`. Honest, BPE-aware counterpart to the older whitespace-atom claim. Lower is better.

Encoders used:

* **`cl100k`** — `cl100k_base`. The tokeniser GPT-3.5 / GPT-4 / Claude legacy use.
* **`o200k`** — `o200k_base`. GPT-4o and the o-series.
* **`gpt2`** — the smaller BPE that LLaMA derivatives share their byte-pair shape with at this granularity. (Llama 3's own tokeniser is HF-gated; this is a conservative proxy that over-counts a few percent.)

All counts use `encode_ordinary` — special-token sequences inside string literals stay literal data.

## How to read these numbers (the honest version)

The earlier whitespace-atom claim — 'Python ~15 / C ~12 / NURL ~4 tokens for add two ints' — counted source atoms, not BPE subwords. These numbers are the BPE-aware version of that claim. The result is uncomfortable: **on Python's home turf, BPE-aware token counts for NURL are not consistently better than Python.** Sieve and json_parse take roughly 2× as many tokens in NURL as in Python; the LCG inner-loop case is the closest to parity (0.89-0.90× on the modern encoders) because that benchmark is dominated by arithmetic operators the BPE doesn't merge well for either side.

Why:

1. **NURL is not in the corpus.** `cl100k_base`, `o200k_base`, and `gpt2` were all trained on huge Python / Rust / JS corpora. Their BPE has merged the common token sequences of those languages into single tokens (`def `, `function `, `for i in range`, `let mut`, `=>`). NURL gets none of those merges and every keyword-shaped token in NURL source decomposes back to individual character pairs.
2. **The atom-count framing rewarded NURL for using single-char operators.** A BPE that has seen Python `range(1, 101)` thousands of times encodes it as 4 tokens; NURL's `< k n` is also ~3 tokens because the BPE has never learned the merge.

Caveats that go the other way:

* These benchmarks are small (3 files, ~150-500 lines each). A large NURL stdlib codebase would have repetitive `( vec_push [T] ...)`-style calls that a NURL-aware tokeniser would learn to merge. The numbers above are the worst-case for NURL — they represent a corpus-zero baseline.
* The Rust column for `json_parse` (1140-2065 tokens) is dominated by Serde derive macros and explicit type signatures the other languages don't need. Rust-on-BPE is not a fair like-for-like.
* NURL/Python parity on a benchmark the BPE was trained on Python for is still a real positive signal — but a much smaller one than the original atom-count framing suggested.
